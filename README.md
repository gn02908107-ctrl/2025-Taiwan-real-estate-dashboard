# 🏠 2025年度全國房地產交易分析 Dashboard

用政府公開的實價登錄資料，打造一個可互動篩選的全國房地產交易分析工具，
涵蓋全台 21 縣市、S1~S4 共四季的交易資料，並整合機器學習模型，
提供依歷史交易特徵估算行情的估價工具，以及可用自然語言查詢統計數字的問答助理。

**🔗 [線上 Demo](https://taiwan-real-estate-dashboard-kmu6tjceclycvdbic6s5zn.streamlit.app/)**

## 專案動機

台灣的實價登錄資料是公開的，但原始資料格式複雜、欄位多、且分散在不同檔案中，
一般人很難直接從中看出房價的趨勢或區域差異。這個專案的目標是把這些原始資料
清理、整合成一個資料庫，並做成一個任何人都能上手操作的互動式 dashboard，
讓使用者可以自己篩選縣市、行政區、房屋類型、季度，快速看到想要的房價洞察；
再進一步用迴歸模型學習歷史交易的定價規律，做成一個可以輸入房屋條件、
估算合理行情的工具。

## 主要功能

網頁分成三個頁籤：**📊 圖表分析**、**🏷️ 房屋估價工具**、**💬 問問看**
（問問看需設定 Groq 金鑰，沒設定時自動隱藏，不影響其他功能）。
左側篩選條件只影響「圖表分析」頁籤。

### 資料視覺化

- **多維度篩選**：季度（S1~S4）、縣市、行政區、房屋類型（中古屋/預售屋）、
  是否含車位，皆可自由組合篩選。所有條件**預設為未選擇**，選齊之前畫面只會
  提示還缺哪些條件，避免一開始就載入全國 24 萬筆資料而讓圖表過於雜亂
- **動態圓餅圖**：呈現交易筆數佔比，選擇單一縣市時自動切換為該縣市的
  行政區佔比，選擇多個縣市時則顯示全國各縣市佔比
- **各行政區平均單價比較**：長條圖呈現，滑鼠移上可看到精確單價（萬元/坪）
- **S1~S4 價格走勢折線圖**：依「行政區 x 房屋類型」分色呈現多條趨勢線，
  圖上直接標示數值，方便比較不同區域、不同季度的漲跌
- **中古屋 vs 預售屋比較**：同一張圖比較兩種房屋類型的單價差異
- **原始資料表**：可自選要顯示的欄位，門牌僅顯示到路名（隱藏巷弄號等細節）、
  日期欄位轉換成可讀格式，並可下載完整版 CSV

### 房屋估價工具

- 用隨機森林迴歸模型（中古屋、預售屋分開訓練），依「行政區、房屋類型、
  車位、建物型態、季度、坪數、格局、樓層、屋齡」等特徵估算單價
- 兩種估價模式：
  - **快速行情查詢**：選擇坪數區間，其餘條件（格局、樓層、屋齡）自動
    帶入該地區/類型/坪數區間的歷史中位數，操作最簡單
  - **個人化估價**：坪數可自行輸入實際數字，貼近特定房屋條件估價
- 所有選項同樣預設為未選擇，選齊後才會出現「開始估價」按鈕

### 問問看（自然語言問答）

用 Groq 的 `openai/gpt-oss-120b`（tool use）讓使用者用中文提問，例如
「台北市大安區的中古屋平均單價是多少？」「基隆市預售屋單價最貴的前五個行政區？」。
**模型不直接回答數字**：它只負責挑選並呼叫 5 個查詢函式，數字全部由程式對資料計算：

1. 單一行政區＋房屋類型的平均單價與交易筆數
2. 單一行政區的 S1~S4 各季走勢與漲跌幅
3. 兩個行政區的平均單價比較
4. 某縣市或全國的行政區單價排行（最貴／最便宜）
5. 同一行政區含車位 vs 不含車位的單價差異

問答固定使用全部四季、含／不含車位合併的資料，**不受左側篩選影響**，畫面上有標示。
每則回答下方有「查詢細節」摺疊區，可看到實際呼叫的工具、參數與原始結果。

**回答品質的防呆設計**

- 找不到行政區或同名行政區橫跨多縣市（如台中市／台北市都有大安區）時，工具回傳候選，
  模型必須回問使用者，不能自行猜測；資料未涵蓋的縣市會直接告知
- 樣本數少於 10 筆的結果會註明「僅供參考」；排行榜會排除樣本數不足的行政區，
  排除後或本來就湊不滿要求名數時，會如實說明（兩個原因彼此獨立，不用因果連接詞連在一起）
- 問題超出 5 種查詢範圍（預測未來房價、買房建議等）時，會明確說出使用者要的是什麼、
  這裡做不到；問到特定房屋條件（坪數、樓層、屋齡…）的估價時，引導改用「房屋估價工具」頁籤
- 支援多輪對話（保留最近 3 輪純文字歷史），使用者對回問的簡短回覆能接上前文

**公開部署的保護機制**（Groq 免費方案每日 20 萬 token，實測每題約 5 千）

- 通行碼（預設需要，未設定時頁籤隱藏）、每個 session 限制題數（預設 5 題）
- 相同問題全站共用快取，命中時不呼叫 API 也不計題數
- 額度用完（HTTP 429）等錯誤只顯示「今日額度已用完，請稍後再試」，原始錯誤只寫進伺服器 log

**驗證與已知限制**

- 27 項工具數字與獨立 SQL 直接查詢的交叉比對全部一致；19 題端到端測試
  （`python qa_assistant.py`，會實際呼叫 Groq）涵蓋基本查詢、防呆、排行榜、估價導向、多輪對話
- LLM 行為對 system prompt 的措辭很敏感：實測曾發現「估價導向」的規則讓模型把
  「台北市火星區」簡化成「火星區」，干擾了行政區傳遞規則，最後是把估價規則的適用範圍收窄，
  並在行政區規則明確補上「縣市要原樣傳入」才修正。因此每次改 prompt 或換模型，都要重跑這些測試
- 依賴免費額度與特定模型，Groq 更換或下架模型時需在 `GROQ_MODEL` 設定新的模型名稱
- 目前已知但未修的兩個小限制：問到資料未涵蓋的縣市（如連江縣）時，回答不會列出目前
  涵蓋的全部 21 縣市；行政區名稱完全找不到候選（零候選）時，模型的重新詢問行為不一致。
  兩者都確認不會造成錯誤或捏造的數字，只是使用體驗不夠完整，暫時記錄下來而不優先修正

## 資料來源與處理

- 資料來源：內政部不動產交易實價查詢服務網（實價登錄）
- 資料涵蓋：全台 21 縣市，S1~S4 四季，中古屋/預售屋，含車位/不含車位，共 332 張資料表
- 資料清理重點：
  - 篩選出「住家用」且交易標的為「房地(土地+建物)」或「房地(土地+建物)+車位」的資料
  - 將坪數與單價從公制單位換算為台灣慣用的「坪」與「萬元/坪」
  - 處理原始 CSV 中欄位數不一致的髒資料列（`on_bad_lines`）
  - 解決不同縣市存在同名行政區的問題（例如台北市、基隆市皆有「中正區」），
    改用「縣市 + 行政區」的複合欄位避免資料混淆
  - 修正「建築完成年月」等民國年欄位因數字型態推斷而遺失前導零的問題，
    寫入資料庫前強制以字串型態讀取
  - 將中文樓層文字（如「三層」）與部分來源的阿拉伯數字樓層格式統一轉換為數值
  - **台東縣命名重複問題（已於 2026-08-30 修正）**：`data['縣市'].nunique()` 原本算出
    22（實際只涵蓋 21 縣市，未涵蓋連江縣），追查後發現 S4 的台東縣資料被同時存成
    「台東縣」與「臺東縣」兩組共 8 張表，S1~S3 則一律用「臺東縣」；逐一比對這 4 對
    表格後確認內容 byte-for-byte 完全相同，是同一批資料存了兩次，並非兩批不同交易。
    進一步把「台→臺」正規化後比對全部 332 張表的縣市字串，確認台北市、台中市、
    台南市等其他縣市沒有類似問題，台東縣是單一事件。修正方式為刪除 S4 底下 4 張
    「台東縣」重複表格，只保留跟 S1~S3 一致的「臺東縣」版本（資料表總數由 336
    降為 332），完整診斷紀錄見 [regression_report.md](regression_report.md)。

## 部署與效能優化

部署到 Streamlit Community Cloud 後，因免費方案記憶體限制約 1GB，App 曾因
同時載入全國 24 萬筆交易資料與兩個隨機森林模型（`n_estimators=200`）而超出
資源限制。解法是把重複值多的文字欄位（縣市、行政區、房屋類型、建物型態等）
轉換為 pandas 的 `category` 型態以降低記憶體用量；過程中也發現 `category`
型態不支援直接用 `+` 做字串合併，需在該處局部轉回字串型態再合併，
避免影響其他地方已優化的欄位型態。

**`category` 型態的 `groupby` 陷阱**：對 `category` 欄位做 `groupby` 時，
pandas 2.x 預設 `observed=False`，會把「篩選後已經沒有資料的類別」也列出來，
造成只選台北市，圓餅圖圖例、長條圖與走勢圖卻出現全國 300 多個行政區；
pandas 3.x 預設改為 `observed=True`，本機（pandas 3.0）完全看不出問題，
部署環境才會重現。解法是所有 `groupby` 明確寫 `observed=True`，不依賴版本預設值。

問答功能也不共用 dashboard 的完整資料：`qa_assistant.py` 每張表只讀 2 個原始欄位
（鄉鎮市區、單價），加上季度、縣市等衍生欄共 7 欄，文字欄位轉成 `category`，
24.5 萬筆約 9.8 MB（同樣資料用一般字串約 29.3 MB），
避免在免費方案的記憶體限制下多載一份全國資料。

## 建模方法與結果

分別針對中古屋、預售屋訓練隨機森林迴歸模型（預售屋因交易當下通常尚未完工，
不採用屋齡特徵），並與線性迴歸、XGBoost 做公平對照比較，完整報告見
[regression_report.md](regression_report.md)。

| 房屋類型 | 模型 | 測試 R² | RMSE | MAE |
|---|---|---|---|---|
| 中古屋 | 線性迴歸 | 0.675 | 12.17 | 7.25 |
| 中古屋 | 隨機森林（調參後） | 0.805 | 9.44 | 4.57 |
| 中古屋 | XGBoost（調參後） | 0.780 | 10.02 | 6.00 |
| 預售屋 | 線性迴歸 | 0.920 | 8.44 | 5.79 |
| 預售屋 | 隨機森林 | 0.981 | 4.15 | 2.15 |
| 預售屋 | XGBoost（調參後） | 0.978 | 4.43 | 2.57 |

建模過程中的重點決策：

- 中古屋隨機森林原始版本有過擬合現象（訓練/測試 R² 差距 0.138），
  用 `RandomizedSearchCV` 調整 `min_samples_leaf` 後改善至 0.012，
  以少量準確度換取更可靠的泛化能力
- 線性迴歸在測試集上出現少數不合理的負值預測（單價不可能為負），
  隨機森林則因預測機制（葉節點樣本平均）不會產生此問題，但也因此
  無法預測訓練資料範圍以外的極端值
- **交叉驗證分數選模型的陷阱**：用 `RandomizedSearchCV` 調 XGBoost 超參數時，
  單純擴大搜尋範圍後，中古屋選到的「贏家」交叉驗證平均測試分數最高，
  但訓練/測試 R² 差距高達 0.167（過擬合），而且加大 `n_iter` 也沒改善——
  因為問題不在抽樣次數，是選贏家的規則本身只看平均分數、沒看訓練/測試差距。
  改成「先篩選交叉驗證差距 ≤0.1 的候選，再從中選測試分數最高者」才解決，
  過程詳見 [regression_report.md](regression_report.md) 第 2 節
- **模型定位**：這是依歷史交易特徵估算行情的橫斷面迴歸模型，
  不是時間序列預測，無法推算未來（如 2026 年）的房價走勢

## 技術棧

- **Python**：資料清理與整合（pandas、numpy）
- **SQLite**：儲存全國資料，取代原本零散的多個 CSV 檔案
- **Streamlit**：建立互動式網頁 dashboard
- **Altair**：繪製可客製化的圖表（折線圖數值標籤、圖例、hover 提示格式等）
- **scikit-learn**：迴歸建模（線性迴歸、隨機森林）、超參數搜尋
- **xgboost**：迴歸建模（梯度提升樹），與線性迴歸、隨機森林做公平對照比較
- **joblib**：模型序列化與存檔
- **Groq API**（`groq` 套件，`openai/gpt-oss-120b`）：問問看的 tool use 問答
- **truststore**（選用）：本機 TLS 憑證錯誤時使用，不列在 `requirements.txt`

## 如何執行

1. 安裝套件：
   ```bash
   pip install -r requirements.txt
   ```
2. 確認 `Database/全國房屋實價登錄資料.db` 路徑正確（`Database` 資料夾需與
   `dashboard.py` 放在同一層）
3. 執行：
   ```bash
   streamlit run dashboard.py
   ```
4. 瀏覽器會自動開啟 `http://localhost:8501`

提醒:如果本機執行時遇到 CERTIFICATE_VERIFY_FAILED 這類 TLS 憑證錯誤,額外執行 pip install truststore 即可解決

### 啟用「問問看」（選用）

不設定也能正常使用另外兩個頁籤。要啟用問答功能，在 `.streamlit/secrets.toml`
（已被 `.gitignore` 排除，請勿 commit；部署到 Streamlit Cloud 則填在 App settings → Secrets）加入：

```toml
GROQ_API_KEY     = "你的 Groq 金鑰"      # 必要；沒設定時「問問看」頁籤隱藏
QA_ACCESS_CODE   = "自訂通行碼"           # 預設需要通行碼；沒設定也沒開放公開時，頁籤隱藏
# QA_PUBLIC      = true                  # 選用：設成 true 就不需要通行碼，對所有訪客開放
# GROQ_MODEL     = "openai/gpt-oss-120b" # 選用：Groq 換模型時改這裡
# QA_SESSION_LIMIT = 5                   # 選用：每個 session 最多可提問幾題
```

執行問答的端到端測試（會消耗 Groq 額度，可指定題號只跑部分）：

```bash
python qa_assistant.py          # 跑全部 19 題
python qa_assistant.py 6 7 18   # 只跑第 6、7、18 題
```

## 未來可以延伸的方向

- 加入地圖視覺化（依經緯度標示交易熱點）
- 增加「總價」相關分析，而不只是單價
- 累積更多季度的歷史資料後，嘗試時間序列預測方法，補足目前模型
  無法推算未來價格走勢的限制
- 估價結果加上可信度提示（例如該預測落在訓練資料中的百分位）
- 問問看目前的題數限制只綁單一連線（重新整理就重置），公開部署可再加全站每日總量上限
- 問答的測試目前靠關鍵字檢查加人工讀回答，可再建立更完整的自動化評估
